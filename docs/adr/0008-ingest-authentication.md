# ADR-0008 — Bearer token for ingest auth, not HMAC

**Status:** accepted · **Date:** 2026-08-05 · **Departs from the brief — argued below**

## Context

`POST /api/ingest` writes to a stranger's YouTube playlist. Unauthenticated, anyone who learns the URL can fill it with anything. The brief calls authentication non-negotiable, which is right, and offers "a shared secret or HMAC signature".

The threat model is specific and worth stating, because it determines which control is appropriate:

| Threat | Real? |
|---|---|
| Someone discovers the URL and posts to it | **Yes** — the primary threat. URLs leak: logs, screenshots, browser history, a shared Shortcut. |
| Someone on the network reads or tampers with the request | No — TLS handles this. Both targets are HTTPS-only. |
| Someone replays a captured request | Marginal — a replay adds an already-added video, which dedupe absorbs. |
| A malicious client crafts a bogus payload | Yes, but authorisation is the control, not signing. |

## Decision

**A long random bearer token in the `Authorization` header, compared in constant time.** HMAC signing is *available* as opt-in hardening but is **not** the default and is not required by any shipped client.

```http
POST /api/ingest
Authorization: Bearer <INGEST_TOKEN>
Content-Type: application/json

{"text": "check this out youtu.be/dQw4w9WgXcQ", "source": "ios-shortcut"}
```

- `INGEST_TOKEN` is 32 bytes of CSPRNG output, base64url. Generated by the deployer with a documented one-liner; never generated by, committed to, or defaulted by this repo.
- Compared with a constant-time equality check, so the comparison can't be turned into an oracle.
- Absent or wrong → `401`, with no detail about which.
- Rate limited per token: fixed-window counter, `INGEST_RATE_LIMIT_PER_MINUTE` default 30. Well above any human's sharing rate, low enough to make brute-force pointless against a 256-bit secret.
- Never logged. The request logger redacts the header by name.

### Why not HMAC by default — the argument

The flagship iOS client is a Shortcut, and **Shortcuts cannot compute an HMAC-SHA256 without contortions**. There is no native hashing action that takes a key. The workarounds are all bad in the same way:

- Embed a `Run JavaScript on Web Page` step — requires a web page context that a share-sheet action doesn't have
- Call out to a scripting app — a paid third-party dependency in a "15 minutes from fork to working" flow
- Route through a proxy that signs — another deployment

So requiring HMAC means either the iOS Shortcut cannot be built, or its setup guide grows a page of scripting that most people will fail at. **A security control that makes the flagship client unbuildable is a net loss**, and the resulting temptation — "just turn auth off to get it working" — is far worse than the marginal gain.

And the gain *is* marginal, because of what HMAC actually buys over a bearer token here:

- **Confidentiality and tamper-resistance:** already provided by TLS.
- **Replay protection** (with a timestamp + nonce): the only real addition. Its value against this threat model is close to zero — replaying a share re-adds a video that dedupe already rejects.
- **Secret not sent over the wire:** genuine, but the wire is TLS, and the secret sits in plaintext in the client's configuration either way. HMAC protects against a compromised TLS terminator; if an attacker controls that, they can also read the request body and forge new ones.

The honest summary: HMAC would add ceremony proportional to a threat that TLS and dedupe already cover, at the cost of the most important client. **The brief permits a shared secret; this takes that option deliberately, not by default.**

Opt-in HMAC (`INGEST_HMAC_SECRET`) is still implemented, because it costs little and someone will legitimately want it — a Telegram-only or PWA-only deployment where every client is JavaScript and can sign trivially. When set, signed requests are required and the shipped Shortcut is documented as incompatible.

### Telegram's separate path

The Telegram bot doesn't use `INGEST_TOKEN`. It authenticates two ways at once: a `TELEGRAM_WEBHOOK_SECRET` in the webhook secret-token header (proving the request came from Telegram), and an allowlist of chat IDs (`TELEGRAM_ALLOWED_CHAT_IDS`, proving *which human* is talking). Without the allowlist, anyone who finds the bot could write to the playlist — the bot's username is discoverable by design, so this is a real and easy mistake.

## Rejected

**Google OAuth session as ingest auth.** Elegant — the user is already authenticated. Rejected because a Shortcut cannot hold a session cookie or perform a refresh, and §12 rules out user accounts beyond Google OAuth.

**Unauthenticated with an unguessable URL path.** Capability-URL-as-auth. Rejected: URLs leak into logs, `Referer` headers, and history in ways headers don't, and it can't be rotated without reconfiguring every client.

**mTLS.** Correct and unusable on a phone.

**IP allowlisting.** Mobile IPs are dynamic. Non-starter.

## Consequences

- Every client is trivially configurable: one header, one value. The Shortcut has a `Get Contents of URL` action with one header. The PWA stores the token. `curl` works for debugging.
- Token rotation means updating each client by hand. Acceptable for a handful of clients; documented in [SECURITY.md](../../SECURITY.md).
- The token is a bearer credential in a Shortcut on a phone — as safe as the phone. Its blast radius is bounded to "can add videos to one playlist", which is the right amount of damage for a stolen credential in this system.
- `401` responses are rate-limited too, so the endpoint isn't a free oracle.

## Revisit if

- **iOS Shortcuts gain a native keyed-hash action.** Then HMAC becomes free and this decision flips.
- **A deployment is exposed to real hostile traffic** rather than being personal infrastructure with an obscure hostname. Then opt-in HMAC plus a timestamp window becomes the recommended configuration.
- **The bearer token proves to leak in practice** in a way the threat model missed.
